## 1. The two trees

| | Path | Notes |
|---|---|---|
| BFBB (host game) | `D:\bfbbpc\bfbb` | Battle for Bikini Bottom PC port. Run `bin\bfbb.exe`. |
| TF2 (Source SDK 2013) | `D:\tf2\source-sdk-2013` | The mod. Run from `game\mod_tf`. |

- BFBB is the authoritative world. TF2 supplies the mercenary: movement, weapons, and the health pool.
- The bridge is loopback UDP between two processes: BFBB listens on **27501**, TF2 on **27500** (`BRIDGE_PORT_*` in `iTF2BridgeProto.h`).
- **BFBB only opens the bridge when the environment variable `BFBB_TF2BRIDGE` is set** (any value). Without it every bridge call is a no-op, so a normal run is untouched.
- BFBB is launched from `bin\`, so start TF2 first (it has to be connecting), then BFBB with `set BFBB_TF2BRIDGE=1 && bin\bfbb.exe`. Both sides log to their own consoles; `bfbb_bridge_debug 1` on the TF2 console prints the traffic.
- The user's `sb.ini` currently has player damage turned **off** (`TakeDamage`), on purpose: while the bridge owns player health, BFBB must not drain its own pool or the player dies twice. Do not "fix" that.
- `roadmapmessage.txt` at the BFBB root is the original ChatGPT checklist plus the early design discussion (MVPT arenas, knockback ownership, damage model, bungees, hazards). It is historical: a status note at the top names this file and the roadmap, and its still-open items are folded into the roadmap's "Parked design decisions and future tasks".

### The upstream line, and the port

BFBB now tracks **upstream treedome `1ab82a27`** (2026-10-22), merged in `082dcc10` on branch `upstream-upgrade`.

- The fork used to sit on a flattened copy of treedome `84522edc` (2026-09-24) with **no shared ancestry** in git — `git merge-base HEAD upstream/treedome` was empty, so a merge had no base to work from. The port declared one with a one-off local graft (`git replace --graft <root> 84522edc`), ran a real three-way, and dropped the graft once the merge commit existed.
- **The fork has ancestry now**: `git merge-base HEAD upstream/treedome` is `1ab82a27`. Future syncs are ordinary merges — `git fetch https://github.com/joeyballentine/bfbb.git treedome:refs/remotes/upstream/treedome`, then merge. Do not re-graft.
- What came in: 171 commits, 960 files, and the bulk of it is `fac8c6fc` (10-14), the port of zcanann's game code. The HB00→HB01 transition the old build broke is fixed there, which is why this could not be cherry-picked.
- 48 files conflicted. The four that touch gameplay are `zNPCGoalRobo.cpp`, `zNPCGoalStd.h`, `zNPCHazard.cpp`, `zNPCSupport.cpp`; 43 PC-port files took upstream wholesale because the fork had changed none of them since its last upstream merge; `iPadHostSDL.cpp` was resolved in place because it carries `iTF2BridgeApplyPad`.
- Two decisions the merge made that a future reader will otherwise undo: the mon cloud's damage gate stays fork-side (`flg_hazard & 0x2000` only) so the buddy arm still runs when the player is outside the cloud, and `zNPCGoalRobo` keeps one `DamageNPCKnockBack` per tick because the decompiled code calls it twice.

Re-verify on this baseline before trusting anything below: the HB00→HB01→HB02 transitions, a talk box (E/R/right-mouse), robot knockback, buddy damage, spawn placement, jelly hitboxes, and the `bfbb_coll_info` numbers — the port moved `xBound`/`xCollide`/`xMemMgr` code, so the chunk/repair tuning measured on the old tree may not carry over.

## 2. Builds

### BFBB

```bat
REM from D:\bfbbpc\bfbb — what the user runs (configure + build). No argument means
REM x86 with D3D9 and GL3 in one exe; the existing x64 directory was configured as
REM build-release.bat D3D9 x64.
build-release.bat
build-release.bat D3D9 x64
```

The backend set is baked into each build directory's CMake cache, so use the same arguments the directory was created with; different ones reconfigure that directory instead of making a new one.

Incremental, what an agent should use:

```bash
cd /d/bfbbpc/bfbb && ninja -C build-release bfbb
```

Build the **exe** in the x86 tree you play, not `bfbb_game`. A static library resolves nothing: a function declared in one file and defined in another with a mismatched signature links into `bfbb_game.lib` happily and only fails when `bfbb.exe` is linked, so `ninja bfbb_game` is not a verification of a cross-file change (this is exactly how a broken `zTF2Bridge_ParticleDamageSource` got through once). `build-release` is x86 and links through ninja; `build-release-x64` cannot (see the resource problem below).

Build directories are per configuration and all copy their output into `bin\`: `build-release` (x86), `build-release-x64`, `build-debug`. The build is clang-cl + ninja; `tools\pcbuild.bat` sets up the MSVC/SDK environment and `VCPKG_ROOT=D:\vcpkg`.

**Known environment problem:** `ninja ... bfbb.exe` fails at *Building RC object … FAILED* with no message. It is not the resource script: the `rc.exe` on the SDK path (a 10.0.10011 binary that lives under a 10.0.26100 directory) compiles `bfbb.rc` fine when called directly. The problem is the rule CMake generated in this build directory. Because the C++ compiler is clang-cl, CMake uses `cmake -E cmake_llvm_rc`, which preprocesses the `.rc` with clang and then invokes the resource compiler with **llvm-rc style arguments** — `-MD -MF <depfile>`, `-I SOURCE_DIR`, `/fo` — and the target here is the MSVC `rc.exe`, which rejects them (RC1107) without ever printing the reason through ninja. Either point `CMAKE_RC_COMPILER` at `C:\Program Files\LLVM\bin\llvm-rc.exe` and reconfigure, or work around it:

```bash
# 1. the .res, straight from the script (MSYS must not rewrite /fo into a path)
cd src/SB/Core/pc/res && MSYS2_ARG_CONV_EXCL="*" \
  "/c/Program Files (x86)/Windows Kits/10/bin/10.0.26100.0/x64/rc.exe" \
  /fo D:/bfbbpc/bfbb/build-release-x64/CMakeFiles/bfbb.dir/src/SB/Core/pc/res/bfbb.rc.res bfbb.rc
# 2. ninja's own link line, which is in D:\bfbbpc\bfbb\build-release-x64\_link.py
cd /d/bfbbpc/bfbb/build-release-x64 && python _link.py
```

Sanity check the result with `llvm-objdump -h bin\bfbb.exe`: it should be about 3.8 MB with `.text` near 3.0 MB, `.rdata` near 0.5 MB and a `.rsrc` of about 32 KB (the icon). A tiny exe, or a missing `.rsrc`, means the link or the resource step went wrong. `ninja bfbb_game` on its own is always safe — the game logic lives in the library, so a *compile* error surfaces there before any of this. It stops short of the link, though, so it cannot catch an undefined or mismatched symbol; only the exe link can.

### TF2

The user builds the mod's `Debug|x64` configuration in Visual Studio; output is `game\mod_tf\bin\x64\server.dll`. Nothing else picks up bridged changes.

Compile-only check without the IDE (x64, W4, warnings visible, no link):

```bat
cd /d\tf2\source-sdk-2013\src\game\server && "D:\tf2\source-sdk-2013\src\_server_win64_tf.bat"
```

Run it from **`src\game\server`**, not `src`: the include paths in the rsp are absolute but the source list is relative (`tf2bridge\tf2bridge_server.cpp`), so the wrong cwd gives `C1083: Cannot open source file: 'tf2bridge\tf2bridge_server.cpp'` for every bridge file while everything else still compiles. Under bash the bat also needs its full path with `cmd //c`, and the `vswhere.exe is not recognized` line it prints is harmless if `cl` runs.

`_server_win64_tf.bat` calls `vcvars64.bat` then `cl @_server_win64_tf.rsp`; the rsp is `/c /Zs /W4 /WX- /Wv:18` plus every include path and the source list, ending in `tf2bridge\tf2bridge_server.cpp` and `tf2bridge\tf2bridge_net.cpp`. A clean exit means it compiles; it does **not** produce a DLL and does not prove the change works in game.

There are two checkouts of these sources and a change must land in both: the Freebuff worktree (where an agent edits and reads diffs) and the live tree `D:\tf2\source-sdk-2013` that the user actually builds. A file edited only in the worktree compiles there against the *old* live copy and proves nothing — copy it across and recompile before claiming a check. `diff` them to see what is pending.

### Protocol headers are duplicated

`iTF2BridgeProto.h` exists twice, byte-identical:

- BFBB: `src/SB/Core/pc/iTF2BridgeProto.h`
- TF2: `src/game/server/tf2bridge/iTF2BridgeProto.h`

Edit one and copy it to the other (`cp` in bash), never by hand. Check with:

```bash
diff -q src/SB/Core/pc/iTF2BridgeProto.h /d/tf2/source-sdk-2013/src/game/server/tf2bridge/iTF2BridgeProto.h
```

There is no version field in the packets (each has a magic and a session), so a protocol change means **both sides must be rebuilt and restarted together**; a stale side silently drops the other's packets.

## 4. Verified working (in game, by the user)

- Rocket Launcher: rockets collide with JSP floor and walls, splash renders, rocket jumping works; BFBB's own splash rendering no longer fires because rockets die on impact, and the NPC proxies absorb it instead. Accepted as-is.
- Grenade Launcher: pipes bounce off geometry, detonate on direct contact with a proxy, and also detonate on a bounce into a proxy. Stickies attach to JSP and bounce off proxies.
- No invisible geometry, no frame-rate collapse.
- Player damage, death and respawn: robots and hazards deal 25 per hit through `bfbb_player_damage_unit`; the pain sound, flinch, HUD direction arrow and knockback all work; BFBB owns the death (fade, rewards, checkpoint, respawn) and TF2 stays dead until `BRIDGE_STATE_PLAYING` says SpongeBob is back, then force-respawns onto him.

## 5. What the last session changed

1. Robot hits were classified as hazards: the bridge tested `baseType == eBaseTypeVillain`, but robots are `zNPCCommon` whose base type is `eBaseTypeNPC`, so every robot hit went out as `npcId 0` / `DMG_GENERIC` — silent, no arrow, no knockback. Both types are accepted now (`zTF2Bridge_ReportPlayerDamage`).
2. Forced death bypasses the hit funnel. `zEntPlayer_Damage` refuses while cheat mode is on, while the hit cooldown is up, while a control-off is active (taxi, springboard, bungee, bubble bowl, trampoline) and while the player stands in a teleport box, and it only spends health when `g.TakeDamage` is on. Any of those left TF2 dead with SpongeBob standing until the 12 s respawn timeout. The death body is now `zEntPlayer_PlayerDied()`, shared by the funnel and by `zEntPlayer_ForceDeathByBridge()`, which zeroes health, clears both timers and calls it directly — plus one stdout line if a missing model makes it retry.
3. TF2's dead intent writes a literal `tfhealth 0` instead of `GetHealth()`.
4. Per-robot damage, first pass. BFBB now owns a table (`sRobotDamage` in `zTF2Bridge.cpp`) keyed by `SelfType()`, and the values are **TF2 health**, not BFBB chunks: fodder 25, hammer and ham-spin 50, tartar 40, glove 40, chuck 60, monsoon 45, arf 60, arf-dawg 30, bomb bot 80, bzzt 40, slick 40. A hit from a listed robot is flagged `BRIDGE_PLAYER_HIT_ABSOLUTE`, so TF2 applies it as-is instead of multiplying by `bfbb_player_damage_unit`; hazards and unlisted robots still go through that convar. The hit packet also carries the source's four-character `npcType`, which the debug line prints.
5. Knockback now scales with the hit: `bfbb_player_knockback` is the shove for a 25-health hit and the impulse is multiplied by `damage / 25`, clamped to 0.6–3.0, so a bomb bot throws the player about three times as far as a cattleprod. New `bfbb_player_damage_scale` multiplies incoming robot damage for playtesting without touching either table.
6. Two follow-ups from the first in-game test of item 5 (damage went up on hammer and bomb bot, their shove did not):
   - The shove was skipped when the robot's reported origin was within one unit of the player. That is exactly the point-blank attackers — the hammer's swing and a bomb bot's burst happen inside the player's hull, so the offset held no direction and the impulse was silently dropped. The fallback is now: robot origin if it is at least eight units away, otherwise the player's horizontal velocity reversed, otherwise straight back from where they are looking. The scale is untouched by the choice.
   - The `CBaseEntity::TakeDamage: with inputInfo.GetDamageForce() == vec3_origin` lines were ours, not a stray game bug: `DMG_CLUB` declares a physics-force hit and the info carried no force. The type is now `DMG_CLUB | DMG_PREVENT_PHYSICS_FORCE`, which is the engine's documented way of saying the hit has no physics force on purpose (TF2 does the same for burns, the flamethrower and syringes). Pain sound, flinch and the HUD arrow are unaffected. The force is also filled with the shove vector, which `CTFPlayer` copies into `m_vecTotalBulletForce`, so a robot kill throws the corpse.
   - The debug line gained `dist=`, `dir=` and `push=`, so a hit that does not move the player can be read from the console instead of guessed at. First log with it: bomb bot `sent=80 tf2=80 hp 125 -> 45 dist=128 dir=npc push=618` and hammer `sent=50 tf2=50 hp 25 -> 0 dist=59 dir=npc push=412`. The numbers and the direction path are correct, so the direction bug is dead — but the user still could not feel either shove.
   - Ground friction was only half of it, and lifting the player did nothing on its own. `CGameMovement::CategorizePosition` only lets go of the floor when the upward velocity beats `NON_JUMP_VELOCITY` (140): below that it traces two units down, finds the ground again and keeps the player standing, so the next tick's `Friction` spends the impulse (a 400 u/s shove dies in about a quarter second, some twenty units). The old upward part was 0.25 of the base — 50 u/s on a fodder hit — so the lift was undone on the very next tick. That is why a 618 push measured correctly in the log and read as nothing.
   - The shove is now built to leave the floor: upward is `MAX(push * 0.5, bfbb_player_knockback_up)`, new convar `bfbb_player_knockback_up` default 268 (exactly a jump, the same floor airblast applies through `JUMP_MIN_SPEED`). A grounded hit also *replaces* the player's velocity (`SetAbsVelocity(vecPush)`) instead of adding to it, because walking into the robot aims the other way and an additive impulse is then mostly spent cancelling the player's own ~300 u/s; airblast stomps velocity for the same reason. An airborne hit stays additive, so a second hit juggles instead of overwriting the first. The debug line gained `onground=` and `vel=before -> after`, which separates "no shove was applied" from "a shove was applied and the player still did not move". Verified in game: the player is now visibly tossed.
   - Second in-game report: it lands, but every hit reads the same, and a bomb bot that bursts behind the player throws them backwards. Two separate causes.
   - Direction at point blank. The origin offset is inside the player's hull for a bursting bomb bot or a hammer swing, so the fallback reversed the player's own movement -- and a player running away from a chaser was therefore thrown back into it. The hit packet now carries the robot's facing (`dirX/Y/Z`, from `npc->frame->mat.at`), and a point-blank hit pushes along it: a robot that lands a hit is facing the player, so its facing is away-from-the-robot at any range. Reversing movement is kept only as the last resort, for a robot that reports no facing. The debug line prints `dir=facing` when that path was taken.
   - Shape. Melee and explosions shared one shape, so a hammer launched like a bomb. TF2 now has `sShoveShapes`, keyed by the four-character NPC type, giving each a vertical and a horizontal value: fodder 150/1.0 (a stumble), tough fodder 150/1.0, hammer and ham-spin 170/1.2, glove 150/1.0, arf 170/1.1, arf dawg 240/1.0, tartar 170/1.0, bzzt 150/1.0, monsoon 200/1.0, chuck 300/0.8, slick 260/0.9, bomb bot 340/0.7. Unlisted robots keep `bfbb_player_knockback_up` (268) with no horizontal scaling. The melee `up` values sit just above the 140 re-ground threshold on purpose: enough to leave the floor so friction cannot spend the shove, not enough to read as a launch.
   - `dirX/Y/Z` is a protocol change: both sides rebuilt and restarted together. Compiles clean on both sides (BFBB `ninja bfbb_game`, TF2 `_server_win64_tf.bat`); the shape and direction changes are not yet tested in game.
   - Third in-game report: the shapes read right, single-hit robots are done. Two gaps left. (a) Every robot can be named on a hit except tubelet and chomper. (b) Those two are also the wrong shape — a flame and a gas cloud shove nobody.
7. Fire and gas now land as robots, and deliberately do not shove. Tubelet's flame spiral and chomper's gas are the only two robots whose player damage does not come from an NPC-owned hazard: they hurt through `xParCmdDamagePlayer` (`zParCmd.cpp`), which calls `zEntPlayer_Damage(NULL, 1, NULL)` with **no source at all**. A sourceless hit is exactly what the bridge calls a hazard, so TF2 took them as `DMG_GENERIC` — no pain sound, no damage arrow — and the packet carried no `npcType`, which is why those two were also the only hits a log line could not name. The particle command now asks `zTF2Bridge_ParticleDamageSource()` (in `zTF2Bridge.cpp`) for the nearest live tubelet, tube slave or chomper within 12 units of the particle and passes it as the source, so the hit reaches the bridge as a real robot hit. Nothing else changed for them: a named robot is already `DMG_CLUB`, which is where the pain sound and the arrow come from. Every other particle system keeps the sourceless call, so goo, pits and spike traps are untouched, and the three types are the only ones tested — a hazard landing near a robot is not blamed on it.
   - In `sShoveShapes`, tubelet (`NTR9`), tube slave (`NTR:`) and chomper (`NTR?`) are `0.0 / 0.00`, which now means "this hit does not shove": pain sound and arrow, no velocity. That is the behaviour asked for — fire and gas do not launch you the way a hammer does.
   - Damage: tubelet 12, tube slave 12, chomper 15 per accepted hit, throttled by `g.DamageTimeHit` (0.5 s). These are placeholders for the tick/DoT numbers in §6a, which need a packet that can carry a damage type and a duration. Tubelet's resurrection blast shares the 12 because the packet cannot yet say which of its two attacks landed.
   - No protocol change (`npcType` already existed), so a stale TF2 build still talks — but the shape table lives on the TF2 side, so without its rebuild these two keep the 268 no-shape shove. BFBB exe plus server.dll.
8. The tubelet is three robots, and its two attacks had to be separated. `zNPCTubelet` (`NTR9`, the top one) owns the health and the blast; `zNPCTubeSlave` (`NTR:`, the spinning bottom one) runs the flame spiral. The blast is the hazard `NPC_HAZ_TUBELETBLAST`, spawned by `zNPCGoalTubeAttack::MaryzFury()` and handed the tubelet as owner, and owned hazards damage through `zEntPlayer_DamageNPCKnockBack(npc_owner, ...)` — so the blast already reached TF2 as a robot hit, it just had a `0/0` shape and did not shove. The flame is the particle path above.
   - New flag `BRIDGE_PLAYER_HIT_NO_SHOVE` (`0x4`), set by the particle command through `zTF2Bridge_NoteParticleHit()` right before it damages the player. Fire and gas never shove, and the flag does not depend on the particle-to-robot lookup succeeding; TF2 treats a no-shove hit as physical (`DMG_CLUB`) even with `npcId 0`, which is what gives the flame and the gas their pain sound and damage arrow in every case. The particle's own position is sent as the hit source, so the arrow has a direction even when no robot is named.
   - The lookup radius went 12 → 24. A tubelet's blast ball alone reaches seven units from the tower and the particles spread further; twelve was likely why the flame stayed silent.
   - `sShoveShapes`: `NTR9` is now `340 / 0.70`, a bomb bot's kick, because that entry is the resurrection blast. `NTD0` (duplotron's death explosion, `NPC_HAZ_DUPLOBOOM`, also NPC-owned and therefore also a robot hit) gets the same `340 / 0.70`. `NTR:` and `NTR?` stay `0/0`; both attacks are flagged no-shove anyway, so those entries only cover a contact hit that is not a particle.
   - Damage is still 12 for the tubelet, shared by the flame and the blast: the packet cannot say which of the two landed. The blast therefore shoves like a bomb bot but costs 12 — split them with an attack id before tuning the number.
   - Flags only, the packet size is unchanged, but both sides must be rebuilt to agree on the new bit.
9. In-game test of §5.8: nothing appeared to change. Flame and gas still silent, tubelet blast still no shove, duplotron shoved but weaker than a bomb bot. Weak-but-present duplo shove is what the *default* shape looks like, so the explosion hits were arriving without a matching type; the binaries were current, so the type really is not what the code assumed.
   - The two blasts no longer depend on the robot type. `NPCHazard::HurtThePlayer()` now sets `BRIDGE_HITKIND_EXPLOSION` for `NPC_HAZ_TUBELETBLAST` and `NPC_HAZ_DUPLOBOOM` (`zTF2Bridge_NoteHitKind`, new flag `BRIDGE_PLAYER_HIT_EXPLOSION` = `0x8`), which TF2 turns into the bomb-bot shape (`sExplosionShove`, 340/0.70) and a physical damage type whether or not the owner could be named. The hit position is the hazard's own centre, so the shove points away from the blast.
   - One note function replaces the particle-only one: `zTF2Bridge_NoteHitKind(kind, pos)` with `BRIDGE_HITKIND_NONE` / `_FIRE` / `_EXPLOSION`. The particle command sets `_FIRE`; the hazard sets `_EXPLOSION`.
   - Both sides now print a build stamp at startup (`bfbb: tf2bridge build 2026-10-25-hitkind` and `[bfbb] server build 2026-10-25-hitkind`), and BFBB prints one line per accepted hit: `[bfbb] hit id=… type=… flags=… dmg=… kind=F|X|? src=x,y,z`. `kind=F` is fire/gas, `X` an explosion, `?` a plain hit. That distinguishes "BFBB never sent it" from "TF2 dropped it", which is the question this round could not answer.
10. The explosion flag works (§5.9, verified in game: the tubelet blast and the duplotron now knock back) but felt weak, and the flame and gas were still silent. Both had one cause left, and it is not `xParCmd`.
   - **The tubelet flame and the chomper gas are NPAR pools, not the particle command.** They damage in `zNPCSupplement.cpp`: `NPAR_Upd_TubeSpiral` (tubelet flame spiral) and `NPAR_Upd_DogBreath` (chomper gas), each calling `zEntPlayer_DamageNPCKnockBack(NULL, 1, &npdata->pos)` when a particle is within half a unit of the player's centre. The source is literally NULL, so every `xParCmdDamagePlayer` change made since §5.7 never ran for them — the `kind=F` path had nothing to attach to. Both callsites now note `BRIDGE_HITKIND_FIRE` and pass `zTF2Bridge_ParticleDamageSource(&npdata->pos)` as the source, so the hit is named, takes the robot's damage number (12/15) and is physical without a shove.
   - **Blasts were scaled like weak hits.** Knockback scales with `damage / 25`, and a hazard reports one BFBB chunk (25 health) — the bottom of the scale — while a bomb bot reports 80 and sits on the 3.0 ceiling. Two hits with the same shape therefore differed by 3×.
   - In game the flame and gas are now correct (pain sound, arrow, 12/15 per hit, no shove), and the explosions throw — but not as far as wanted. An explosion now bypasses the damage scaling and the shape table entirely: `bfbb_player_knockback_blast` (default 550, horizontal) and `bfbb_player_knockback_blast_up` (default 320) are fixed and live-tunable, so the feel is dialled in from the console instead of with another rebuild. 420 horizontal is a bomb bot's burst, so the default is already a third further and flatter; the `NTR9`/`NTD0` shape entries stay as the fallback for a hit that arrives without the flag.
   - Still true: the NPAR lookup is positional (24 units) and only considers tubelet, tube slave and chomper, and the blast damage number is still one BFBB chunk (25 TF2 health) even though it now shoves like a bomb bot.
11. Hit cadence, and the flame split from the blast. Every hit in BFBB passes one gate — `globals.player.DamageTimer`, set to `g.DamageTimeHit` (1.5 s in sb.ini) — so the three attacks the game re-applies *every frame* were 1.5 s apart only because of it, and each one also blocked every other hit while its timer ran. A fodder's prod could swallow a flame tick, and a flame tick could swallow the hammer.

21. Robot model hulls exported, so a proxy can be seen as the robot instead of a box (BFBB 15:05, server.dll 15:08, client.dll 15:09).
    - **Why the box was there, and why it is not enough.** BFBB's own collision for a robot is its `xBound` -- a box, and exactly what a spatula or a laser ray test hits -- so the box is *correct* for hits. It is not the robot: arms and head sit inside it, and because its centre is the robot's origin it sits slightly off a model that is not centred on it (the standing-still offset reported in §5.18 is this, not lag). The shape a robot looks like has to come from its model.
    - **The triangles come from RenderWare, not a new exporter.** Each robot's `xModelInstance` chain is walked, each atomic's geometry supplies triangles, and `iModelVertEval` is called with the root bone matrix temporarily set to identity -- the same trick `xModelAnimCollRefresh` uses for `anim_coll` -- which leaves the vertices in **robot-local** space, pose included and position/facing removed. Up to `BFNM_MAX_TRIS` 4000 triangles and 4096 vertices per atomic; one evaluation per model asset, on the first frame the bridge sees it, not per frame.
    - **File:** `<bfbb dir>/bfbb_npcmodels.bfnm` -- `"BFNM"`, version 1, then repeat `{ u32 modelId, u32 triCount, float verts[triCount][9] }` of raw BFBB units. Append-only, one record per model the moment it is seen, so a robot that spawns mid-level appears without a restart; **truncated on the first model of each run** so a stale record can never be read as this run's. TF2 polls it twice a second and re-reads only when its size changes, and a record whose vertices are not all in the file yet is ignored until the next poll rather than half-read.
    - **Protocol:** `BridgeNpcTarget` gained `modelId` (the NPC asset's `modelInfoID`, then the instance's `modelID`, then `0x80000000 | type` as the last resort, so two robots of one type still share a shape) and `yaw` (`atan2(at.x, at.z)`, the same number the player packet uses). 8 bytes per target; both sides rebuilt together, stamps `2026-10-28-npcmesh`.
    - **Drawing:** `bfbb_npc_draw` (default **2**) is a bitfield -- 1 the old collision box, 2 the model hull, 3 both -- and `bfbb_coll_draw` now draws only JSP triangles. Server-side, every frame, like the box. Budget: 2400 overlay lines a frame, split between the proxies being drawn (`BFBBNpc_BeginDraw`), 400 triangles each at most, sampled evenly, so a crowd of robots thins every hull rather than truncating. Hulls are orange, boxes stay blue.
    - **Rotation is one multiply, and it was checked on paper:** the stored vertices are already Source space, and a BFBB yaw is a rotation about Source +Z by the *same* number, applied at draw time. A robot facing BFBB +X (yaw 90) has its hull's forward along Source +Y, which is the same answer the axis mapping gives for `at`.
    - **Known limits.** (a) The pose is frozen at first sight -- idle or mid-stride -- because re-exporting per frame would mean writing the file 60 times a second; animation tracking needs a low-rate re-export, not built. (b) Hits are still the box in BFBB's own game (see §5.22 for the TF2 half).

22. TF2 weapon traces resolve against the robot's model, not its box (server.dll 10-29).
    - **Why the box could not stay.** The bound BFBB reports is the box its own ray test uses, and in game it is visibly larger than the robot: shots landed on empty air beside a robot, and the blue cage engulfed the model. That costs hits both ways, so the proxy's rays moved onto the mesh.
    - **One collide per model, in the robot's own space.** `BFBBNpc_GetModelCollide` compiles the same `bfbb_npcmodels.bfnm` triangles the hull draws into a `CPhysCollide` with `PolysoupCreate`/`ConvertPolysoupToCollide`, cached by model id, built on first ask. **Plain soup, not MOPP** (`bfbb_coll_mopp` does not apply): MOPP assumes a closed solid and would fill the air between a robot's limbs and under its hat with collision that is not there, which is the exact error being removed.     - **Fallbacks.** A proxy keeps plain box collision until its model has been exported: `BFBBNpc_GetModelCollide` returns NULL while the record is missing, the flag is not set, and rays behave exactly as before. A model whose soup converts to nothing is remembered as NULL with a `collide FAILED` warning rather than retried on every trace.

On a bridged level that point is under the JSP, so the player came back at the bottom of the world while SpongeBob reappeared on the level -- and the placement follow could not fix it, because it copies SpongeBob's *live* position and BFBB does not have him back yet at that instant.
    - **The state packet now carries the level's spawn.** `GetPlayerSpawnPoint` reads the `PLYR` asset the same way `zGameSetupPlayer` does -- the *last* PLYR asset in the level, not the first -- and reports `spawnX/Y/Z` plus `spawnYaw` (`ang.x`, radians in the asset, degrees on the wire) with `BRIDGE_STATE_HAS_SPAWN`. Sent every frame, so a checkpoint reload updates it without TF2 having to ask at the right moment. 16 bytes; both sides rebuilt, stamps `2026-10-29-plyrspawn`.
    - **Where the host is put on a respawn.** A real player (`!IsBot()`) on the 0->1 alive transition is placed on SpongeBob's position when BFBB is `PLAYING` with `GAMEPLAY` set (a checkpoint reload moves him, and that is the spot to copy), and on the PLYR asset when BFBB has no live player to copy -- which is exactly the respawn gap. Snapped onto the collision mesh, +4 units, `MOVETYPE_WALK`, then `m_placed` is claimed immediately so BFBB adopts the position instead of holding its own.
    - **Bots are excluded by design.** They are not the bridged player; a TF2 bot must keep using TF2's spawn points. `UTIL_GetListenServerHost()` returns the real host anyway, so the guard is about intent, not a bug.
    - **This also makes startup placement deterministic**: the same path runs on the first alive frame, so the host appears on the spawn asset instead of wherever SpongeBob happened to be mid-load.

24. Every TF2 spawn goes to BFBB's spawn, including the ones with no death (server.dll 10-29, `2026-10-29-spawnany`).
    - **§5.23 only covered dying.** In play the remaining way under the map was `mp_waitingforplayers` ending (and `mp_restartgame`, and a listen server loaded while BFBB was still starting): TF2's `RoundRespawn` respawns a **live** player, so there is no dead frame, `m_wasAlive` never goes false, and the respawn placement never ran. The host was dropped on the Valve spawn point under the JSP and stayed there, which on an HDD is also the case where BFBB has SpongeBob falling through the void for a second before it moves him.
    - **A respawn with no death is a teleport.** The frame hook now remembers where the host ended the previous frame (after every teleport it made itself) and treats a jump over 256 units in one tick as TF2 moving a live player. That is the only signal a `RoundRespawn` leaves; per-frame walking and knockback are an order of magnitude under it, and every bridge teleport writes the new origin first so it can never trigger on its own work.
    - **One placement, three triggers.** A dead -> alive respawn, that foreign teleport, and BFBB reaching `PLAYING` (its spawn is only meaningful once it has a player in play) all call the same `PlaceHostOnBridgeSpawn`, which goes through `GetRespawnPosition`: SpongeBob's position when BFBB is playing, the PLYR asset when it is not.
    - **The pending snap no longer chases a falling player.** When a placement is pending and BFBB is *not* driving the host (`bfbbHasControl`), the snap used to copy BFBB's live position, which during a load can be SpongeBob mid-fall through the world. It now uses the spawn asset too; only a BFBB-controlled stretch (cutscene, forced walk) rides the live player, because that is the one case where the unrevealed position is the right one.
    - **`GetRespawnPosition` refuses to guess.** With neither `PLAYING` nor `HAS_SPAWN` (BFBB still loading) it returns false: nothing moves, the host waits where TF2 put it, and `m_placed` stays unclaimed so BFBB keeps holding its own player. That is the deliberate fallback -- TF2's spawn point is a real place, BFBB's mid-load position is not.
    - **The respawn hold now needs a bridge.** `bfbb_player_respawn_hold` is gated on `GAMEPLAY`; before this, a session with no BFBB at all set the hold on every death and delayed TF2's respawn by `bfbb_player_respawn_timeout` (12 s). If the hold is on and gameplay disappears mid-death, the override is released with `SetRespawnOverride(-1.f)` instead of stranding the corpse.
    - `bfbb_bridge_debug 1` prints `host placed at (x y z) (BFBB player|PLYR asset)` for every placement and, before it, `TF2 teleported the host with no death; ...` when the teleport trigger is what fired. That line appearing during normal play (a teleporter, say) is worth reporting: TF2 does not get to choose where the bridged player is.

25. Jellyfish are NPC targets (BFBB exe only, no protocol change).
    - **Why they were missing.** Every path that mirrors, damages, splashes or hitscans an NPC was gated on `IsTF2BridgeRobot`, an explicit list of the 18 robot types. Jellyfish are `zNPCAmbient`, not `zNPCRobot`, so a shot went through one and TF2 never saw it — no proxy, no hull, no damage. Nothing else about them needed inventing: `zNPCJelly` carries `hitpoints` from its ini, `zNPCCommon::Damage` accepts `DMGTYP_SIDE` from SpongeBob (its `flg_vuln` keeps both the any-damage bit and the side bit), and the model exporter `DumpNpcModel` only ever needed a `zNPCCommon` with a model.
    - **`IsTF2BridgeCritter` / `IsTF2BridgeTarget`.** A critter is `NPC_TYPE_JELLYPINK` (`NTA0`) or `NPC_TYPE_JELLYBLUE` (`NTA1`); a target is a robot or a critter. The five places that mean "can this be shot" (state packet, proxy hit lookup, rocket splash candidate, both hitscan/projectile sweeps) now use the target check. The blocks that are about robots specifically — the knockback override, the chuck casts, the `-knockback offered-` line — still use the robot check, because ambients have no knockback goal and no hover to compensate for.
    - **A hit costs it one hitpoint.** `zNPCGoalJellyBumped::Enter` does `hitpoints--` and sends it to the bumped goal; below 1 it dies the way BFBB kills a jelly. So a jelly's durability is its ini's `pts_damage`, unchanged from BFBB, and `tmr_invuln` (0.5 s, set by `zNPCCommon::Damage`) is what keeps a rapid-fire weapon from stripping it in one frame. Being hit also makes it angry, which is the game's own reaction.
    - **Damage to the player.** Jelly zap already reached TF2 before this change — `zNPCGoalJellyAttack::ZapperUpdate` calls `zEntPlayer_DamageNPCKnockBack`, which runs `zEntPlayer_Damage`, which reports to the bridge at 0.9 s into the animation. What it lacked was a number: jellies were not in `sRobotDamage`, so the hit took the chunk path and TF2 scaled it by `bfbb_player_damage_unit`. Now pink is 10 and blue 12 (blue is the 3.5-speed chaser in the jelly scenes). Repeat zaps are gated by `g.DamageTimeHit`, not by a bridge window, because BFBB's own timer refuses the extra calls.
    - **Slot pressure.** `BRIDGE_MAX_NPC_TARGETS` is 32 and a jelly field can hold more critters than that, so the state list is built in two passes — robots first, critters second. A swarm can thin itself out of the packet but can never push a robot out of it.
    - **No TF2 rebuild.** The packet layout is unchanged and the proxy code is type-agnostic (`IsTF2BridgeRobot` was never consulted on that side), so `server.dll` from §5.24 talks to this build. The jelly hull appears through the same `bfbb_npcmodels.bfnm` path, and `bfbb_npc_hitbox 1` gives it mesh rays the moment its record is written.
    - **Verified in game by the user**: proxies, hulls, damage and the zap feedback all work as described; every enemy family in the game is now bridged.
    - **Pending, deliberately not applied yet**: blue jelly is **25**, not 12 — settled after playing with them, and held for the next round of changes rather than a one-line rebuild now. `sRobotDamage`'s `NPC_TYPE_JELLYBLUE` entry is the single number to change.

26. A level audit for the first real-level pass (BFBB exe only, off by default).
    - **Why.** Every level played so far is `bfbbtest`. A real level is made of things the bridge has never collided: SIMPs, PLATs, trigger volumes, portals, warp boxes, pendulums, hangables. Those do not fail loudly — a PLAT is simply not a surface you stand on, a trigger is never entered, a hazard that hurts by collision never fires, and a warp box does not know you are in it. The damage funnel is already generic, so what is missing is the *trigger*, not the reporting. At this stage the useful output is a list, not a fix.
    - **`BFBB_TF2BRIDGE_AUDIT=1`** (same env-var convention as the other bridge switches) turns on three things:
      - **One line a second** with the player's position, the scene, the entity count, and per-kind counts for the kinds a real level is made of (PLAT, TRIG, PICK, BUTN, DSTR, SAVE, TELE, PORT, VOL, HANG, PEND, DYN, plus NPC and VILL), each with the distance to the nearest of that kind, whether it is above or below, its subtype, and **`col`/`-col`** — whether BFBB would collide it at all (`xEnt::collType`). A PLAT that reads `-col` is driven by hand code, which is also why TF2 cannot see it. Distances are Source units, via the scale TF2 sends, so they compare with the tf2bridge convars.
      - **A scene-change line**, `audit scene %08x -> %08x, N s unseen (playing=…)`: the gap is the load, measured from the last frame the old scene was there to the first frame the new one is. This is the transition timeline, and it prints even when the cutscene hides it.
      - **A refused-hit line** from `zEntPlayer_Damage`'s own gates — `cooldown`, `control` (a control-off is running: taxi, springboard, bungee, bowl, trampoline), `teleport` (inside a warp box), `cheat` — one per source per two seconds. A hazard that never calls the funnel prints nothing at all, which is the difference this line exists to make.
    - **The scene tracker runs unconditionally**, audit or not: on a scene change it clears the hit windows, the pending knockback, the burn exposure and the pending hit kind. Those hold **raw entity pointers**, and a level load frees and reallocates them — a stale window would match a different NPC that happened to reuse the address and silently swallow one hit in the new level. That is a real fix, not a diagnostic, and it is the first thing a level change needed.
    - **What it does not do:** it does not add PLAT/SIMP collision, does not touch movement, and prints nothing in a normal session. It is the instrument for deciding what to do next, in the order the user chose: whatever blocks reaching the next warp first.

27. A session log the user can hand back after a real playthrough (both sides, on by default).
    - **Why a file and not the console.** The audit prints what the level is made of; a session is a *timeline*, and the question afterwards is always "what was I standing on when that happened, and what did the other engine think at that second". That needs both processes' clocks in one place, and it needs to survive the console scrolling away.
    - **One file, both halves, appended.** `D:\bfbbpc\bfbb\logs\session_YYYY-MM-DD.log`, one line per event, `HH:MM:SS.mmm <bfbb|tf2> <KIND> key=value ...`. Each line is a single open/append/close of one formatted line, so two processes interleave between lines and never inside one, and the wall-clock stamp is what orders the two sides. `BFBB_TF2BRIDGE_LOG=0` turns it off; any other value is the file to write instead (both processes read the same variable, so setting it makes them agree on a different file). See §10 for the kinds and how to read it.
    - **BFBB contributes**: `SESSION`, `LEVEL` (every scene change with the gap the load took, written whether or not the audit env var is set), `SPOT` (position every 15 s), `NEAR` (each level entity the first time it comes within reach — kind, asset id, subtype, distance, above/below, whether the player is inside its box, `col`/`-col`), `HIT` (mirrors the accepted-hit printf, with the hit kind), `REFUSED` (mirrors the refused-hit line, ungated by the audit flag), `HITNPC` (each TF2 shot applied to a robot, with damage, knockback multiplier and whether it lived), `DEATH`/`RESPAWN`.
    - **TF2 contributes**: `SESSION`, `MAP`, `LEVEL` (the mirror of BFBB's scene change: proof this side noticed), `PLACE` (where the host was put and whether the source was `bfbb_player` or `plyr_asset` — the answer to "I started under the map"), `SPAWN`/`DEATH`, `SPOT` (host position, health, scene, BFBB's position and how old the packet is), and `WARN` when BFBB goes silent mid-level.
    - **`bfbb_note <text>`** in the TF2 console is the user's own bookmark: it writes a `NOTE` line with the text, the host's position, class, team, health, scene and BFBB's position. Typed while standing on the thing that is wrong, it lands between the two `NEAR` lines that describe the same spot from BFBB's side.
    - **Bounded on purpose**: the file stops at 24 MB, `STAT`/`DYN` lines are capped at 4000 per process (a kelp field cannot fill it), and a `NEAR` entry is forgotten five seconds after leaving its radius so coming back is a new line rather than a silence. Logging, like the audit, never runs unless the bridge is on.
    - **One bug found while building it** (already fixed, in the audit's scene tracker): the per-attack hit windows hold raw entity pointers, and a level load frees and reallocates them. Cleared on every scene change now — see §5.26.
    - **The first run crashed BFBB, and that is fixed too** — the trail's entity walk followed a stale pointer. What it was and how the address was named: §5.28.
    - **The first real session was recorded** (2026-10-29, HB00 -> HB02; the user's notes are the `NOTE` lines in it). It proved the timeline, the scene handshake and `PLACE` out, and it is what found the three things in §5.29: talk boxes cannot be answered from inside TF2, `NEAR` repeats while you stand still, and the walk's `WARN` was counting model-less objects rather than the bad pointers it is for.

28. The entity walk followed a stale pointer (crash fixed; `xMemAddrInHeap`).
    - **Symptom.** `bfbb: CRASH -- exception 0xc0000005 at 009AE4A7 [bfbb.exe+0x2ce4a7]`, access violation *reading* `0x450D0663`, main thread, with the bridge on. The release link carries no `/DEBUG`, so the crash handler printed every frame as `?`.
    - **How it was named.** Relinking the same objects with `-Xlinker /MAP` (to a separate `-o`, so `bin\bfbb.exe` was untouched) produced a binary of byte-identical size — same layout — and the map put `0x2ce4a7` inside `zTF2Bridge_Frame`. Disassembling `[bfbb.exe+0x2ce4a7]` showed `movss xmm1, [eax]` then `[eax+4]`, `[eax+8]`, then a subtract against `frame->mat.pos`, which is the session log's `NEAR` distance (`pEnt->x - pos->x`) on a pointer that is not an entity. The scenery cap (`sLogSceneryLines >= 4000`) sits in the same basic block, which is what rules out the audit's identical loop. The recipe is at the end of §10.
    - **Cause.** The walk trusted `sc->ents[i]` and then `ent->frame` / `ent->asset` with only a null test. `xMemAlloc` zeroes, so a *fresh* entity is null and skipped — but the entity array outlives the objects it names in windows a frame loop can see through: a scene part-built, or an entity freed with the level before it whose block has been reused since. `0x450D0663` is such a block, read as if it were an `xEntFrame`.
    - **Fix.** `xMemAddrInHeap()` (xMemMgr) answers whether an address is inside one of the game's three heaps. Everything the game allocates for itself comes from them, so an address outside is not a game object; the heaps are reserved *committed*, so a byte inside one is always safe to read even when the object is gone. The walk asks it about `ent`, and about `ent->frame` / `ent->asset` before following either (`TF2Bridge_EntPos`); the audit's copy of the walk and the `HIT` line's position use the same helper. The player's own frame goes through `TF2Bridge_PlayerPos` for the same reason — between a level unload and the player coming back it is not null, only wrong.
    - **The bound query was the other unchecked pointer** on that line: `xBoundGetBox` dereferences an OBB's matrix without testing it. `TF2Bridge_EntBox` answers for SPHERE and BOX, and for OBB only when the matrix passes the heap test.
    - **It reports now instead of crashing.** `WARN walk skipped N unreadable entity pointers (scene=… ents=… first=…)`, at most one per 10 s per process. None in a session means the walk never met one; a stream of them means something is freeing under the walk and the trigger is a different path.
    - **Not reproduced here** — the bridge needs TF2 talking to it, which is the user's own rig. The diagnosis is from the machine code and the map, not from a live catch; the guard cannot fault by construction, but whether it still *reports* the level is only proven by the next run.

29. A talk box can be answered from inside TF2, and two things the first real session log showed wrong.
    - **Symptom.** HB00 -> HB02 went in cleanly and the bridge held the player in the right place, then the run stopped at a text box: BFBB was waiting for a pad press, no TF2 key did anything, and the only way past was to go back to BFBB's window and press the key there. A real level is full of these (every `ztalkbox`, including the tutorial's "press R" prompts), so this blocks progression everywhere, not just in HB02.
    - **Cause.** `iTF2BridgeApplyPad` returns early when the intent carries `BRIDGE_INTENT_OWNS_MOVE`, by design: with TF2 moving SpongeBob, forwarding TF2's buttons into BFBB's pad would make him jump and swing inside a body TF2 is driving. But a talk box reads **nothing else**: `ztalkbox::update_all` takes its press from `globals.pad0->pressed` (`pad_pressed()`), gated by the box's `permit` bit and its `trigger_pads` mode. With the pad path closed, no key of any kind could reach it.
    - **Fix, game layer.** `zTalkBoxWantsPad()` (`zTalkBox.cpp`) answers 1 while a box is up, its permit allows the pad, and its `trigger_pads` mode matches who has the player (`TP_ACTIVE` with a free player, `TP_TRAPPED` with a trapped one) -- the same three conditions `update_all` checks one statement later, so the bridge cannot offer a press the box then refuses. `zTF2Bridge_Frame` sets it every frame through `iTF2BridgeSetPadWanted`.
    - **Fix, pad path.** While that is set, and only then, the owns-move path forwards three keys: TF2 `+use` (E) as **A and R1**, `+attack2` (right mouse) as **Y** (the no of a yes/no box), `+reload` (R) as **B** (the quit). Everything else stays suppressed. A and R1 both, because the state machine consumes A itself (a page of text, the yes) while the tutorial boxes that print an R glyph are wired as links on the R1 event -- offering only A leaves exactly those stuck. A box that listens to one ignores the other.
    - **Why not just send everything while owning movement.** A (jump) and B (spatula) are gameplay buttons in BFBB. Sending them whenever a talk box is *not* waiting is how the puppet starts hopping inside TF2's collision, so the exception is narrowed to the frame window where BFBB is demonstrably asking.
    - **It is in the log**, because this is the one interaction TF2 cannot show on its own: `TALK wants_pad=1` when a box starts waiting, `TALK wants_pad=0` when it stops, and `TALK confirm forwarded` for each E press that arrives while it is waiting. A box that cannot be passed with `wants_pad=1` and no `confirm` line means the key never arrived; `confirm` with no advance means BFBB wants a different button than A or R1, which is the one thing this cannot guess.
    - **`NEAR` was repeating itself, and that is fixed too.** The dedupe table dropped an entry after ten scans -- but it only restamped the scan number when it *wrote* a line, never when it merely saw the object, so everything within reach was written again every 5.5 s. The HB02 log is that, sixty objects at a time. Restamping on sight makes the rule what it always said: one line when something comes into reach, another only after leaving it for five seconds.
    - **`WARN walk skipped` was counting the wrong thing.** 689 of HB00's 805 entities and 729 of HB02's were reported as unreadable; they are not stale pointers, they are objects with no model -- no `frame`, no `asset` -- which can never have a position. The warning now fires only for a pointer that fails the heap test (`TF2Bridge_EntUnreadable`), which is the case that was crashing, and the objects that simply have no position are skipped in silence.
    - **Not verified in game.** Builds clean (`bfbb.exe`, 16:20, BFBB side only -- no protocol change, so `server.dll` does not need a rebuild); the pad path itself is the one already proven by walking, so what is unproven is only whether A|R1 is the button HB02's box wants.

30. The player's bound goes back to a sphere (pickups, triggers and interactive objects), and the golden spatula no longer softlocks.
    - **Two reports, one cause.** Shiny objects and socks were collected the instant they came into reach without ever drifting toward the player, and triggers and interactable objects answered as if the player were somewhere else -- the library's spatula gate firing while the user stood in SpongeBob's kitchen in HB02, with the JSP collision matching exactly on both sides the whole time.
    - **Cause 1: a union.** §5.17 replaced `globals.player.ent.bound` with TF2's hull as `XBOUND_TYPE_BOX`. `xBound` is a union of `xSphere`, `xBBox` and `xCylinder`, so `sph.r` and `box.box.lower.x` are the same four bytes, and every reader that says `.sph` on the player is reading a box.
    - **Cause 2: the game writes that field every frame.** `PlayerCollCheckEnv` widens `bound.sph.r` to 0.65 for the world sweep and sets it back to 0.5 immediately after -- on a box, that is `lower.x` being rewritten to a constant, roughly 0.5, for the rest of the session.
    - **Cause 3: who reads it.** `zEntPickup` takes its magnet range from `plent->bound.sph.r` and its collect range from `4 * plent->bound.sph.r`, so the collect radius became a world coordinate (8 BFBB units, 1280 Source units, at the HB02 position in the log) -- hence instant collection with no magnet. `xBoundUpdate` centres a box at `(lower + upper) / 2`, and with `lower.x` pinned that is halfway between the origin and the player; `xBoundCenter` is an inline in `xBound.h` returning `&sph.center` whatever the type. Teleport boxes, bus stops, NPC glyphs, the boulder, laser bolts and the pickup grid all ask that field.
    - **Fix.** `zTF2Bridge_AfterPlayerUpdate` rebuilds a SPHERE every frame: radius 0.5, centre 0.5 above the feet along the player's `RootUp`, which is the shape `PlayerBoundUpdate` gives it -- applied to the position TF2 actually sent rather than the one the frame's zeroed movement produced. Rebuilt here rather than left to the game because the game rebuilds it from its own lagging position.
    - **What is given up.** Crouching no longer buys a tighter fit against a robot. That was the only reason for the hull, and it needs a bound whose shape the game does not write into. 0.5 BFBB units is 20 Source units against TF2's 16, so a robot stops you four units early -- which is exactly how BFBB plays.
    - **The golden spatula.** `zEntPickup`'s spatula path takes control (`CONTROL_OWNER_REWARDANIM`) and arms `SpatulaGrab01`, which is entered only from `Idle01` and releases control from the callback that ends it. Retail already softlocks if you grab one mid-fall; the bridge pins the position and zeroes velocity every frame, so the player is never standing in idle and the pose never starts. `zEntPlayer_GiveSpatulaBridge()` performs the parts of the reward that outlive the pose in one frame -- the autosave and its failed-save message, and the NPC area notice -- and `zEntPickup` calls it instead of `zEntPlayer_GiveSpatula` while `zTF2Bridge_DrivesPlayer()`. The pose, its camera pan and the music dip are deliberately not performed: those are the reward moment, and they belong to a TF2 taunt once that is built.
    - **Still open.** `BUTN`s stay unreachable while TF2 drives (§6a note), and the deeper reason the player is never "standing" -- the bridge does not tell BFBB's ground state anything -- is untouched: the spatula is fixed by not depending on it, not by making him land.

### 6d. The first real-level pass (next)

Decided with the user on 2026-10-29, after all enemy families were bridged:

- **One TF2 map, BFBB swaps scenes in place.** A TF2 map change is the wrong mechanism: it rebuilds the entity list, forces the class menu, throws away the connection on a listen server, and puts TF2's load on a clock separate from BFBB's own. The in-place swap is already most of the way there — the collision dump is per-scene (`bfbb_collision_%08x.bfcl`) and TF2 reloads when the wanted scene differs, the spawn asset is resent every frame, and proxies are rebuilt from the state packet. Map *variants* buy nothing: the TF2 map only supplies a fallback spawn, sky/lighting, the HUD and an empty box, since the JSP is what you walk on.
- **Order of work:** instrument (§5.26), then one real level, then fix whatever blocks reaching the next warp. Expected first: standing on and riding PLATs/SIMPs, then trigger volumes, then hazards that hurt by collision, then warps.
- **The run itself** (agreed 2026-10-29): a **fresh save starting at HB00 and played forward to JF04**, with the session log on, in the house order "whatever blocks reaching the next warp". King Jellyfish is knowingly out of reach — it cannot be damaged yet — so he is not a bug to chase in this pass, just a wall the run stops at. Instrumentation first: §5.27's log is the output of the run, so nothing here is guesswork afterwards.
- **Loading panel** is the polish after the swap works, not before; see the roadmap's §5 for what was decided (client-side, opaque, level title + still + bar).
- **Multiplayer** is co-op in one scene first, with everyone a copy of SpongeBob, which makes **robot target priority** the first real co-op task. Recorded in the roadmap; not scheduled.

### 6c. Parked, deliberately not scheduled

One line each; the reasoning is in the roadmap's "Parked design decisions and future tasks":

- **MVPT arenas.** Robots wake only when SpongeBob enters an arena radius and go idle when he leaves, so a merc shooting from outside is ignored or has the robot chase SpongeBob. Needs combat awareness fed by bridge hits, with de-aggro on a timeout.
- **Damage model toggle.** BFBB few-hit kills (breaks juggling, overpowered hitscan) versus per-robot health pools (needs a head position for sniper headshots), selectable by convar or options menu.
- **Bungees.** Separate moveset, forced third person; required for some spatulas and socks, so it blocks a full playthrough.
- **BFCL storage and nav-meshes.** Today one collision file per level, regenerated; keeping them could also seed TF2 bot navigation.
- **Fire and hazards.** Pyro damage-over-time delivered into BFBB and rendered on robots; ice floors and slick's oil as ice physics; bounce pads.
- **Multiplayer.** Per-player scenes so two people can be in different levels without a global reset; deep BFBB work.
- **Industrial Park extras.** Sentry build spots, player/bot spawn points as pointer assets, MvM-like opposing spawns.

## 7. Known problems, not yet addressed

- **Ragdolls ignore `bfbb_coll_physics 1`.** They fall through the BFBB JSP; only the living player is collided against it. Client-side ragdoll physics would need the same collision pass.
- **Shots still resolve against the box (§5.21).** The robot's model is exported and drawn, but `xRayHitsBound` in BFBB and `SOLID_BBOX` in TF2 both still use the bound, so a shot at an arm that is outside the box misses and a shot at empty space inside it hits. Fixing it means a mesh test in BFBB and/or a per-model vphysics collide in TF2 -- not started.
- **Floor holes in the cell mesh -- closed at 2048, not explained.** `bfbb_coll_chunksize 2048` is the default and holds the reported spots (§5.17); the covering piece still does not trace on its own, so the underlying VPhysics soup→collide behaviour is unexplained and another spot could still lose a triangle at any cell size. `bfbb_coll_wholemesh 1` is the diagnostic (it lags), and `bfbb_coll_info`/`bfbb_coll_profile` are how a new report should be priced before anything is changed.

## 8. Conventions and hazards

- Branch work stays on `tf2-bridge-damage-work` in both repos. Never claim a build or an in-game test that was not actually performed; the roadmap's update protocol spells this out.
- Do not touch the rocket splash compromise. The user accepted it.
- BFBB's hit cooldown (`g.DamageTimeHit`, sb.ini, default 0.5 s) still throttles robot and hazard reports. It is not the damage number.
- `mp_disable_respawn_times 1` is cosmetic now: the bridge holds the spawn, it does not rewrite the countdown.
- Multiplayer / per-instance level synchronisation is deliberately unprioritised; resets are per machine.
- **A `class`/`struct` forward declaration changes the symbol name.** clang's MSVC mangler encodes the tag kind (`V` for `class`, `U` for `struct`), so a header that says `class zNPCCommon;` and a .cpp that sees the real `struct zNPCCommon` produce `PAVzNPCCommon@@` and `PAUzNPCCommon@@` — different symbols, undefined at link with an error that looks like the function does not exist. Declare forward types with the tag the definition uses; `zNPCCommon`, like most BFBB types, is a `struct`.

## 9. Smoke test after any bridge change

1. Rebuild both sides (both if the protocol changed), restart both processes.
2. Walk and jump in BFBB as the mercenary; camera and stick direction agree. Walk out onto the biggest floor plane you can find, including the spot outside the level: the split mesh (startup line `loaded N collision triangles as M pieces`) should hold you wherever BFBB does. If a spot still drops you, run `bfbb_coll_hole` standing there and keep its output -- it says whether the mesh has a triangle at all, and which collide lost it.
3. Fire a rocket at the floor: it impacts, splash shows, rocket jump works.
4. Bounce a pipe into a proxy: it detonates. Stick one: it does not.
5. Take a fodder hit: pain sound, arrow pointing at the robot, shove. Console shows the hit with a non-zero `npc=`.
6. Take a hammer hit and stand next to a bomb bot when it bursts: both should shove further than the fodder (2× and 3× the base) with no `vec3_origin` warning, and should pop the player off the floor. `dist=` near zero with `dir=velocity` or `dir=view` is the point-blank fallback working; `onground=1` with `vel=` showing the shove in place of the run speed, and the player leaving the floor, is the shove landing. A hammer or fodder hit should knock the player back with only a small hop, a bomb bot bursting from behind (or at your feet) should throw you away from it with `dir=facing`, and `up=` should read 150–170 for melee against 300+ for an explosion.
7. Stand in a tubelet's flame spiral and in a chomper's gas: pain sound and a damage arrow, **no shove** (`push=0`, `dir=none`). The log line shows `flags=` 6 or 7 (ABSOLUTE plus NO_SHOVE) and `npc=` `NTR9`/`NTR:` for the flame, `NTR?` for the gas. Health now drains at about **80/s from the flame** (6 a hit, a tick every 0.075 s) and **10/s from the gas** (5 a hit, every 0.5 s) — the gas is the same rate it had at 15 per 1.5 s, the flame is Pyro-parity. The ouch sound and the screen shine should play a few times a second rather than on every tick; if the player strobes, the reaction throttle is not working. An unattributed hit (`npc=----`) falls back to the stock 1.5 s gate, so it will feel chunky again — that means the lookup missed. `npc=----` with `flags=` still carrying the no-shove bit means the particles were not matched to a robot (24 units from the particle) but the feedback should still be there — that is the difference the flag buys. BFBB prints `kind=F` for each of these hits. They come from the NPAR pools in `zNPCSupplement.cpp` (§5.10); `kind=?` for a flame or gas hit means the damage came from somewhere else again, so keep the line and say so.
8. Let the tubelet revive and blast, and destroy a duplotron: both throw on their own convars, `bfbb_player_knockback_blast 550` horizontal and `bfbb_player_knockback_blast_up 320`, pointing away from the blast — further and flatter than a bomb bot's burst (420 / 340). Tune those two live; `bfbb_player_knockback_blast 0` turns an explosion's shove off. These no longer depend on the robot being named: BFBB prints `kind=X` for the hit, and TF2 applies `sExplosionShove` whenever that flag is set. A blast that does not move the player with `kind=X` in the BFBB log and nothing in the TF2 log means the hit was dropped (check `alive=`/`control=` messages).
8b. Stand under sleepytime's beam: about 50/s of damage, a nudge rather than a throw, pain sound and arrow present. Then let a fodder hit you while the beam is on: both must land. If one swallows the other, the hit window is still being shared between attacks.
8c. Afterburn (**both sides must be the `-burn` build** — the hit packet grew, so a mismatched pair drops every hit silently): brush the tubelet flame and jump straight out — flames on the model and about 3 s of ticking. Stand in it for several seconds — `aft=` climbs toward 10, and leaving then burns for roughly that long. Wake monsoon and take one bolt — 3 s of fire. A Pyro only gets the brief flame, and the chomper's gas must not ignite at all. `aft=` stuck at 0 with `burn=0.08` in BFBB's line means the flag arrived but TF2 did not burn; `burn=0.00` means BFBB never sent it, i.e. the hit was not attributed to a robot. After §5.13 the burn also **takes health** at about 8/s (4 a tick): flames without health loss is the null-attacker rejection coming back, so check that the TF2 build is the one from §5.13 rather than the `-burn` build alone.
9. Die: TF2 waits through BFBB's death and fade, then respawns exactly when SpongeBob does.
10. Stand in goo or fall in a pit: silent, no arrow, immediate kill.
11b. Spawn placement, every case (§5.23, §5.24). `bfbb_bridge_debug 1` prints `host placed at (x y z) (BFBB player|PLYR asset)`; that parenthesis says which of the two answered.
    - **Death.** Die in BFBB (goo or a pit is fastest): the host must reappear on the level where SpongeBob respawns, not under the JSP. A checkpoint reload is the case that prints `BFBB player` — if it prints `PLYR asset` there, BFBB was not `PLAYING` when TF2 came back.
    - **No death at all.** Load the level with `mp_waitingforplayers 1` (the case that still failed) and let the round start: the host must be pulled up onto the level when the freeze ends, with `TF2 teleported the host with no death` immediately before the placement line. `mp_restartgame 1` must do the same.
    - **Either start order.** TF2 first, sitting at the Valve spawn under the map while BFBB boots: the host must stay put until BFBB has a spawn (that is the fallback, not a failure) and then move up when BFBB reaches Play. BFBB first, TF2 second: placed immediately on join.
    - **Fallback.** With BFBB not running at all, TF2 must spawn and respawn normally, with no delay from `bfbb_player_respawn_hold`.
11. Startup placement (§5.14), both orders. Start TF2, load a listen map, let it sit; then start BFBB with `BFBB_TF2BRIDGE=1`. The host must appear where SpongeBob is, and SpongeBob must never move to the TF2 spawn (a jump to somewhere under the level on the first frame means `BRIDGE_INTENT_PLACED` is not being honored). Now the other order: BFBB first, TF2 second. Same result either way. `bfbb_bridge_debug 1` prints `state:` each second; the placement is invisible in the log by design, but the host's position should match BFBB's `pos=` within a few units.
12. Near-camera cleanup (§5.14). BFBB's model should be gone from the view while TF2 drives (`bfbb_player_visible 1` brings it back, `0` hides it again -- neither changes movement). Walk into a robot: BFBB's own collision should stop you at the same distance it always does. Crouching does **not** buy a closer fit any more -- the player's bound is BFBB's own sphere again (§5.30).
12b. Robot hulls (§5.21). `bfbb_npc_draw 2` (the default) draws each robot's own model as orange wireframe at its proxy; `1` gives the old blue collision box; `3` both. BFBB prints `npc model <id>: N triangles` the first time it sees each model, and TF2 prints `npc models: N in file (M new)` as it picks the file up. A robot with no orange hull either has no exported record yet (check `D:/bfbbpc/bfbb/bin/here/bfbb_npcmodels.bfnm` exists and grows) or the proxy is not reaching it. A hull that is the right shape but turned the wrong way means the yaw convention, not the mesh; one that is a different robot's shape means two models share a key. `bfbb_npc_draw 1` beside 2 is the comparison that says whether the box and the model agree -- they should not, and where they differ is where a shot and a robot disagree today.
12b. Robot hitboxes (§5.22). Shoot a robot in the body and in the air just beside it: with `bfbb_npc_hitbox 1` (default) the body registers damage (`[TF2BridgeDummy] proxy hit npc=...` in the TF2 console, the hit line in BFBB) and the air does not -- that is the whole fix. The orange hull from `bfbb_npc_draw 2` is the same shape the ray is tested against, so a shot that hits the wireframe must land and a shot through a gap must not. `bfbb_npc_hitbox 0` puts the old box back for a side-by-side. `tf2bridge_npc_hitbox` with a robot within 512 units prints its model id, triangle count, box and two rays (body = must hit the proxy, above-the-model = must not), which is the check without aiming. A proxy still on its box (rays landing on air) means its model had not been exported yet -- the BFBB console prints `npc model ... collide: N triangles` when it is.
12d. Jellyfish (§5.25, BFBB exe only). In a jelly scene, `bfbb_npc_draw 2` must draw an orange hull on a pink and on a blue jelly, and shooting one must register (`[TF2BridgeDummy] proxy hit npc=...` in the TF2 console, the hit line in BFBB) instead of the shot passing through. A jelly should die after as many hits as its ini says, with BFBB's own bumped/death animation rather than an instant disappearance. Let one zap you: pain sound, damage arrow, no `npc=----`, and pink 10 / blue 12 health — a hit that reads `npc=` with a chunk-scaled number means the damage table entry is not the one being built. `bfbb_npc_draw 1` on a jelly beside `2` is the check that the proxy is the model and not the box.
12e. Level audit (§5.26), on a **real** level — `BFBB_TF2BRIDGE_AUDIT=1` before launching `bfbb.exe`. Expect one line a second (`audit pos=… scene=… ents=… PLAT=n@d+…`) and a line per scene change. Walk a stretch of the level and keep the log; what matters is which kinds appear next to you while you are standing on nothing and falling through, and which read `-col`. A hazard that hurts you should also print a `[bfbb] hit …` line; one that does not hurt you and prints `audit hit refused` reached the funnel and was gated, while one that does neither never collided with you at all — those are three different problems and the log tells them apart.
13. Floor holes (§5.16): stand at one, `bfbb_coll_hole`, then walk in after each of `bfbb_coll_chunksize 2048`, `bfbb_coll_chunksize 4096` and `bfbb_coll_wholemesh 1`. Which of the three holds you up is the answer, and `bfbb_coll_profile 1` reports what whole-mesh movement costs per second if it is the one that works.
14. Session log (§5.27, §10): after launching both, the day's file must exist where both sides write and start with `SESSION begin side=bfbb` **and** `SESSION begin side=tf2` — only one of the two means the paths disagree, and the `log=` field on each line says which path each half chose. `bfbb_note test` in the TF2 console must print `[bfbb] noted: test` and leave a `NOTE` line with a position and a class.
16. Pickups and interactive objects (§5.30). Walk near a shiny object or a sock: it must **drift toward you and then be collected**, not vanish from across the room. Stand next to a bus stop, a teleport box and any "press R" glyph: the prompt must appear where the object is, not somewhere else. Walk a spot where a trigger has fired in the wrong room before and check it now fires where it is drawn.
17. Golden spatula (§5.30). Grab one while running and while in the air. It must collect, count (`Inv_Spatula`), write the autosave ("SAVING GAME" icon may flash for a frame) and play the comment; there must be no control-off, no camera pan and no freeze. ## 10. The session log, and how to read it

`D:\bfbbpc\bfbb\logs\session_YYYY-MM-DD.log` (a session that crosses midnight continues in the next day's file). Plain text, one event a line:

```
HH:MM:SS.mmm <bfbb|tf2> <KIND> key=value ...
```

Distances and positions are **Source units**, in Source's axes, so they match `bfbb_coll_info`, `bfbb_coll_hole` and the tf2bridge convars without conversion. Scene ids are BFBB's, in hex. Both engines append to the same file, so `bfbb` and `tf2` lines sit next to each other in one timeline.

| Kind | Side | Meaning |
|---|---|---|
| `SESSION` | both | a process started; `log=` says which file, so a path mismatch between the halves is visible at the top |
| `MAP` | tf2 | the TF2 map loaded (`name=`) |
| `LEVEL` | bfbb | a BFBB scene change: `to=`, `from=`, `gap=` (seconds the scene was unseen: the load), `ents=` |
| `LEVEL` | tf2 | the same change as this side noticed it (`noticed=1`); the pair is the handshake |
| `PLACE` | tf2 | the host was put somewhere by the bridge, and from what: `from=bfbb_player` or `from=plyr_asset` |
| `SPOT` | bfbb | where SpongeBob is, every 15 s, with health, entity count and play state |
| `SPOT` | tf2 | where the host is, every 15 s, with health, BFBB's position, `bfbbok=` and `age=` (packet age) |
| `NEAR` | bfbb | a level entity first came within reach: `kind=`, `id=`, `sub=`, `d=`, `up=`, `in=` (player inside its box in XY), `top=` (box top relative to the player), `col=`/`-col` |
| `HIT` | bfbb | a hit BFBB accepted and sent: `kind=F` fire/gas, `kind=X` blast, `?` other; `dmg=`, `burn=`, `flags=`, `src=`, `pos=` |
| `REFUSED` | bfbb | a hit that reached the funnel and was gated: `reason=cooldown\|control\|teleport\|cheat` |
| `HITNPC` | bfbb | a TF2 shot applied to a robot/critter: `id=`, `type=`, `dmg=`, `base=`, `kb=`, `alive=` |
| `DEATH` / `RESPAWN` | both | the player down (BFBB) or the host down (TF2), and back |
| `NOTE` | tf2 | `bfbb_note <text>`: the user's bookmark, with position, class, team, health, scene |
| `TALK` | bfbb | a talk box started (`wants_pad=1`) or stopped (`0`) waiting for a pad press, and `confirm forwarded` for each TF2 E press handed to it (§5.29) |
| `WARN` | tf2 | BFBB has gone quiet mid-level (`bfbb_silent=`) |
| `WARN` | bfbb | the entity walk refused pointers it could not read: `walk skipped N unreadable entity pointers`, with `scene=`, `ents=` and `first=` (see §5.28) |

Reading it:

- **Progression** is `grep -E ' (SESSION|LEVEL|MAP) '`. Every level the run reached is a `LEVEL` line, and the load time is the `gap=`.
- **What was around the player** is `grep ' NEAR '`. A kind that never appears in a level was never near, which is not the same as "it exists and does not work".
- **"Something hurt me"** is `HIT` / `REFUSED` / `DEATH` — the three-way split §5.26 describes. Silence in all three means the hazard never touched the player.
- **"My shots do nothing"** is `HITNPC` with `alive=1` and a health that never drops, versus no line at all (the shot missed the proxy).
- **Hazards that only fire when BFBB collides with them** (spike traps, PLAT crushes, busses, bungees) have no line of any kind until the collision work exists: that absence is the expected result of this pass, not a regression.
- Dense kinds (`HITNPC`, `NEAR` under `STAT`/`DYN`) are the ones to filter first when the file is large. `bfbb_note` lines are the fastest way to slice a big file: `grep -n NOTE` gives the line numbers to read around.

### Naming a crash address

`bin\bfbb.exe` is linked without `/DEBUG`, so it ships no PDB and the crash handler's frames come out as `?`. A map file costs nothing and moves nothing: take the link line from `ninja -C build-release -t commands bfbb | tail -1`, add `-Xlinker /MAP:D:/bfbbpc/bfbb/bin/bfbb.map -Xlinker /MAPINFO:EXPORTS`, and point `-o` at a different name so the real exe is untouched. The output is byte-identical in size (same layout, so the addresses still apply), and the crash report's `bfbb.exe+0x2ce4a7` is the map's `0001:002ce4a7`:

```
grep -E "^ 0001:[0-9A-Fa-f]{8} " bfbb.map | awk '{ rva=strtonum("0x" substr($1,6)); if (rva <= 0x2ce4a7) print rva, $2 }' | tail -3
```

The last line is the function that contains the fault; `llvm-objdump -d --x86-asm-syntax=intel --start-address=$((0x400000+0x2ce4a7-0x40)) --stop-address=$((0x400000+0x2ce4a7+0x10)) bfbb_map.exe` reads the faulting instruction. That is how §5.28 was identified: the map gave `zTF2Bridge_Frame`, the disassembly gave `movss xmm1, [eax]` on an entity position.
